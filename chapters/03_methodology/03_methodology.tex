\section{Research Design}\label{sec:research-design} 
This chapter describes the methodology used to empirically evaluate the external reachability and service exposure of an IoT device in a residential IPv6 network configuration. The study follows a controlled case study design, in which a programmable embedded device (ESP32) is used as a representative IoT system. As discussed in Section 2.2, such devices commonly exhibit simplified network stacks and weak service configurations, making them suitable proxies for real-world IoT deployments. The device was systematically configured under different network conditions, while measuring its observability, accessibility, and network traffic visibility in each case. These configurations modify key parameters such as firewall state, access origin, and interaction protocols.
The experimental setup is implemented in a physical laboratory environment using commercial hardware, including a residential router and an external VPS. This approach allows precise isolation of network variables while maintaining environmental control and reproducibility. At the same time, it avoids ethical concerns associated with scanning or interacting with third-party devices on the public Internet. 
The experimental design is structured around a set of progressive scenarios, ranging from an internal baseline to externally reachable IPv6 configurations and a final comparative scenario under IPv4. Each scenario is evaluated based on observable network and service interactions, including reachability at the ICMP level, TCP connectivity, and the presence of application-layer responses, allowing consistent expected results across repeated executions. All evidence is collected in raw form, including terminal outputs, packet captures, and device-level logs.

\section{Testbed Architecture and Threat Model}\label{sec:testbed-threat-model} 
The testbed was built with four main components: an ESP32-based device, a residential router acting as the perimeter network controller, an internal host connected to the same LAN, and an external VPS located outside the residential network. This architecture allowed the behavior of the embedded device to be observed from two complementary perspectives. The first was a local perspective, which made it possible to verify the internal availability of the IoT services and inspect traffic within the LAN, and, when communication between the embedded device and the internal host was not encrypted, to examine the content of the exchanged packets. The second was a remote perspective, representing potential access from outside the residential network.

The target device was an ESP32 microcontroller executing custom firmware developed for this study. Although the implementation is custom, its design follows the IoT service models and practices described in Section 2.2, rather than introducing new mechanisms. The firmware was implemented using the Arduino environment and the ESP32 network stack, including \verb|WiFi.h|, \verb|esp_event.h|, \verb|esp_netif.h|, and the lwIP socket interface. These libraries enabled the management of the WiFi connection, network events, IPv6 initialization, and the creation of TCP services over IPv6 sockets.
Once connected to the wireless network, the device automatically obtains both a link-local address and a global IPv6 address, and logs this information together with its MAC address through the serial output.  This allows direct documentation of the device’s network identity and addressing state within the experimental setup.
At the application layer, the firmware implements two services over IPv6. The first is an HTTP server running on port 80, accessible through the main route ``/'', which returns a simple dashboard with device information. Furthermore, the same server exposes an undocumented endpoint, ``/hidden\_admin'', reflecting a pattern commonly observed in IoT devices~\cite{liu2025eagleye}. The second service is a Telnet-like TCP server on port 23, which requests credentials in plain text and uses default credentials (``admin/admin''). Both services record inbound connections, including the source IPv6 address and remote port, as well as relevant events such as access to the hidden endpoint, authentication attempts, and executed commands. This enables the correlation between what is externally observable at the network level and the evidence generated locally by the device itself.
The residential router is the perimeter component of the testbed. This device provides native IPv6 connectivity and a public static IPv4 address, which is essential for establishing a fair comparison with the IPv4 environment. In the case of IPv6, the router allows the firewall state to be modified explicitly, making this configuration one of the key independent variables of the experiment. In the case of IPv4, incoming connections are not directly possible by default unless an explicit port forwarding rule is configured. Since no such rule was enabled in this experiment, the IPv4 setup provides a useful baseline for contrasting both exposure models without introducing additional configuration elements that fall outside the scope of this study.
Within this established perimeter, an internal host is also present. This host serves a double function. On the one hand, it is used to establish the local baseline of the experiment, meaning that it verifies that the device responds correctly at both the network and application layers before any external reachability test is performed. On the other hand, depending on the scenario, it acts as a passive observer, allowing traffic within the LAN to be captured and analyzed in order to verify whether the information exchanged via HTTP and Telnet remains visible in plaintext. The external VPS, located in a different country and equipped with native IPv6 connectivity, serves as the remote observation point and is used to generate ICMPv6 probes, TCP connection attempts, HTTP requests, and Telnet sessions from outside the residential network.
From this architecture, two complementary observation modes were defined. The first corresponds to an active external observer, represented by the VPS, which attempts to reach the device through its global IPv6 address and evaluate its reachability, TCP connectivity, and response at the application layer. This same external position is also used in the final IPv4 comparison. The second corresponds to a passive local observer within the LAN. This distinction makes it possible not only to evaluate to what extent the device can be reached from outside the residential network, but also whether its communications remain visible inside the local network in the absence of encryption.

\section{Experimental Scenarios}\label{sec:experimental-scenarios} 
The experiment was organized into five progressive scenarios (S0 to S4). Instead of evaluating each network parameter individually, the independent variables, such as the IPv6 firewall state, the origin of access, and the protocol used, are manipulated through these scenarios. In this way, each scenario represents a controlled condition under which changes in device reachability, service visibility, and traffic exposure can be observed.
