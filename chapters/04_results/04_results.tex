\section{Address Assignment and Identifier Exposure}
Upon connecting to a residential WiFi network, the ESP32 successfully completed the IPv6 autoconfiguration process through SLAAC. The logs confirm the assignment of a link-local address as well as a global IPv6 address, together with the MAC address and the parameters observed in Table~4.
\input{chapters/04_results/figures/device_identity_parameters.tex}
The link-local address was assigned first, followed by the global address after the reception of the Router Advertisement. Both addresses coexisted in the interface during all the experimental scenarios.
The interface identifier (IID) of the global address presents a format consistent with EUI-64, derived from the MAC address of the device. (meter referencia)

\section{Internal Baseline and Local Service Availability (S0)}
The ESP32 responds correctly to ICMPv6 probes, and both TCP ports (80 and 23) are reachable, with the implemented services behaved as expected.
\input{chapters/04_results/figures/s0_internal_baseline_results.tex}
Accessing the HTTP root endpoint returns a valid response with device information, and the undocumented endpoint \texttt{/hidden\_admin} is also accessible without authentication. Furthermore, a Telnet session can be established using the default credentials (admin/admin).
All interactions are recorded in the ESP32 logs, which contains source addresses, requested resources, and authentication events. This confirms that the device and its services are fully operational before introducing any external interaction.

\section{External IPv6 Reachability with Firewall Enabled (S1)}
ICMPv6 probes received responses in all attempts (10/10), with an average RTT of 40.8 ms (Table 4.3).
\input{chapters/04_results/figures/s1_external_ipv6_firewall_enabled_results.tex}
However, no transport-layer connectivity was observed. Ports 80 and 23 were reported as filtered, with no TCP responses. HTTP requests timed out, and no Telnet session could be established. The device did not register any incoming TCP connections during this scenario.
Packet captures on the VPS confirmed that only ICMPv6 traffic was exchanged.

\section{External IPv6 Accessibility with Firewall Disabled (S2)}
ICMPv6 connectivity remained consistent, with 10/10 responses and an average RTT of 40.4 ms (Table 4.4).
\input{chapters/04_results/figures/s2_external_ipv6_firewall_disabled_results.tex}
Ports 80 and 23 were reported as open, and both services were accessible from the external host. The HTTP root endpoint returned a valid response, the /hidden\_admin endpoint was accessible without authentication, and the Telnet session accepted the credentials admin/admin.
HTTP responses included device information, and the logs confirmed incoming connections from the external address along with the associated events. Traffic captures showed that the HTTP exchange, including the request to /hidden\_admin and its response, was visible in plaintext.

\section{Local Traffic Visibility and Plaintext Exposure (S3)}
Traffic captures allowed direct observation of HTTP requests, full server responses, Telnet authentication prompts, and credentials in plaintext (Table 4.5).
\input{chapters/04_results/figures/s3_local_passive_observation_results.tex}
The device’s MAC address was visible in the Ethernet headers. Both HTTP and Telnet traffic could be inspected directly without the need for decryption.
\section{IPv4 Baseline Without Port Forwarding (S4)}
The router responded to ICMP probes, confirming network-level connectivity (Table 4.6).
\input{chapters/04_results/figures/s4_ipv4_baseline_results.tex}
Ports 80 and 23 were reported as filtered, and HTTP requests timed out with no response. No direct inbound access to the device’s services was observed under this configuration.

\section{Cross-Scenario Summary}
The results show consistent differences between the internal baseline (S0), external network-level response without application access (S1), external service accessibility (S2), local traffic visibility (S3), and the IPv4 scenario without port forwarding (S4).
\input{chapters/04_results/figures/cross_scenario_comparative_results.tex}
Across all IPv6 scenarios, the device responded to ICMPv6 probes. TCP service accessibility depended on the perimeter configuration. Plaintext traffic was observable in scenarios S2 and S3. In the IPv4 scenario, no direct inbound access to the device was observed.
